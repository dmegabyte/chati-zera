# Project Housekeeping

Проводи безопасную уборку проекта как исследование, а не как автоматическое
удаление. Цель — отделить используемое от исторического, дубликатов и
кандидатов на удаление, сохранив рабочий код, незакоммиченные изменения,
rollback и production-контракты.

## Режимы

- `overview` — по умолчанию. Только read-only инвентарь и отчёт.
- `verification` — локальные проверки, уже определённые проектом или явно
  одобренные пользователем. Анализаторы работают только в report-only режиме.
- `repair` — отдельная задача после явного согласования точного списка файлов,
  owner-layer и проверки. Этот skill сам по себе не разрешает repair.

Если режим не назван, используй `overview`.

## Жёсткие границы

Никогда не делай автоматически:

- удаление, перемещение, архивирование файлов или зависимостей;
- автофиксы, форматирование, `git restore`, `git clean`, `stash`, commit, push
  или deploy;
- установку Ruff, deptry, Vulture, Knip, lychee или других инструментов;
- запросы к production, VPS, внешним API, модели, CRM, MCP, Jivo, Sheets или
  чтение секретов;
- вывод о неиспользуемости только по отсутствию прямого импорта.

Не добавляй plugin, сервис, агента, скрипт или новые permissions ради уборки.
Технические permissions OpenCode важнее текста этого skill.

## Порядок работы

### 1. Зафиксируй границы

До исследования назови:

```text
project: <корень>
area: <одна проверяемая область>
mode: overview | verification | repair
definition_of_done: <какой отчёт или проверка нужна>
do_not_touch: <внешние контуры, защищённые файлы, соседние области>
```

Начинай с project rules и ближайшей документации. Не считай исторические docs,
старые логи или Git commits доказательством текущего production-состояния.

### 2. Сохрани границу Git

Если проект — Git-репозиторий, сначала проверь `git status --short` и
релевантный `git diff --stat`.

- На dirty tree продолжай только read-only анализ и явно перечисли защищённые
  изменения.
- Не смешивай найденные пользователем незакоммиченные изменения с housekeeping
  пакетом.
- Git history сохраняй: старый commit — это rollback/forensic evidence, а не
  кандидат на удаление.

### 3. Собери доказательства

Изучай только одну область за раз и проверяй цепочку:

```text
entrypoint / config / CI / test / documentation / runtime-or-release consumer
```

Для кандидата на удаление нужны минимум два независимых подтверждения, включая
отсутствие актуального consumer. Динамические импорты, plugins, systemd,
workflow, release/rollback scripts, fixtures, generated files и внешние
интеграции считаются возможными consumers, пока не доказано обратное.

### 4. Используй инструменты только как источники кандидатов

- Python: существующие project checks; при отдельном одобрении доступны
  `ruff check`, deptry и Vulture только без `--fix`. Vulture допускает false
  positives и не является доказательством удаления.
- TypeScript/JavaScript: Knip только после доказательства entrypoints и
  динамических imports; результат — список для review.
- Документация: проверяй локальные относительные ссылки. Внешние URL не
  проверяй без отдельного разрешения.

Если инструмент не установлен, сообщи это. Не устанавливай его и не подменяй
его вывод догадкой.

### 5. Выдай компактную карту

Максимум пять приоритетных находок в таком формате:

| Статус | Объект | Доказательства | Owner/consumer | Следующий безопасный шаг |
|---|---|---|---|---|

Допустимые статусы:

- `keep` — доказан текущий consumer;
- `hold` — есть production/release/external/dynamic или неизвестный consumer;
- `historical` — не участвует в активном маршруте, но сохранён для review,
  fixtures, rollback или forensics;
- `candidate` — возможен cleanup, но требуется точная отдельная проверка;
- `blocked_by_owner_input` — не хватает контракта, target или доказательства.

Для каждого `candidate` укажи точные пути и anchors, текущего owner, минимум
один независимый пример/consumer того же класса, минимальную обратимую правку,
проверку и `do_not_touch`.

## Переход к изменениям

`overview` и `verification` заканчиваются отчётом. Перед `repair` пользователь
должен отдельно подтвердить:

1. точную цель и список путей;
2. owner-layer и доказательство, что прямой минимальный fix достаточен;
3. локальную проверку и deliberately excluded work;
4. commit/push/deploy — отдельными разрешениями.

Не заменяй полезный historical test массовым `skip`/`xfail` и не удаляй
покрытие ради зелёного suite. Если текущая проверка смешивает исторические и
активные контракты, сначала предложи разделить их в test boundary, сохранив оба
набора.

## Формат финального отчёта

```text
result: <что доказано>
protected_work: <dirty/внешние/неизвестные поверхности>
findings: <до 5 строк таблицы>
verification: <точные команды и результаты, либо “не запускалось”>
not_proven: <что не доказывает отчёт>
next_safe_step: <один минимальный следующий шаг>
```
